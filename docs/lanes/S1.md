## The remaining contradiction (and its resolution path)

lfstrip's algorithm is correct C: `p=s+strlen(s)` then walk back zeroing
`\r`/`\n`. Correct strlen ⇒ `\r` stripped ⇒ match succeeds. But the compare saw
`\r`. Both cannot be true simultaneously, so one of these holds:

- H_A: lfstrip's `strlen(s)` returned a value ≤ 9 (short) at runtime → `p`
  started at/inside `"]"`… impossible for short values to skip PAST `]`—a short
  strlen makes p start NEARER the string start, and the backward walk would
  then hit `'\r'` at [9]? NO — backward from a shorter end stops at the first
  non-CR/LF byte, which could be `']'` at [8] if strlen counted only through
  `[STRINGS` … i.e., strlen returned **8** (stopped before the final `S`? no—)
  → the precise failing strlen value must be OBSERVED, not deduced.
- H_B: the compared buffer was NOT the one lfstrip stripped (two inbuffers /
  stale frame reuse — D_ProcessDehFile's vs deh_procStrings' local copy).
