# S1 investigation — RESOLVED (2026-08-24)

## Root cause (verified end-to-end)

`crates/wie-cpu/src/jit/lower/gpr.rs::lower_mov` composed store values with
plain `read_gpr`, which returns the FULL 64-bit register. For
`mov r/m8, %ah/%bh/%ch/%dh` the helper then wrote `value.to_le_bytes()[..1]`
= **AL instead of AH**. `lower_xchg`'s memory↔register arm had the same
defect.

Doom Retro's statically-linked MSVC CRT strcpy core
(doomretro.exe `0x140155468..0x1401554ff`) stores string bytes in AL/AH pairs
with `shr $16` between them; every second byte therefore arrived as a
duplicate of its predecessor once that block was JIT-compiled
("Vivisection"→"Viviseettoo", "%.2f."→"%%22..", "Underhalls"→"Under RRaam").
DEHACKED `[STRINGS]` values all pass through this routine (`M_StringCopy` →
CRT strncpy/strcpy and `strdup`), which corrupted most BEX values and made
the `VERSION` key compare fail → empty `s_VERSION` →
`I_Error("The wrong version of …doomretro.wad was found.")`.

The interpreter was unaffected, which is why iced runs looked clean and the
bug appeared only on JIT-hot blocks.

## Summary

Doom Retro exits with "The wrong version of …doomretro.wad was found." because
`s_VERSION` remains empty after DEHACKED processing. Through extensive byte-level
tracing, differential unit tests, and runtime instrumentation, the root cause has
been narrowed to **heap corruption during BEX string duplication** — multiple
`deh_strlookup` entries show fragments of adjacent strings merged into their
values (e.g., `'MAP13: StationnEErth'`, `'Development mooeeOO..'`). `s_VERSION`
is one of the casualties.

## Ruled out

- ~~XMM cross-boundary register loss~~ → fixed (xmm full writeback)
- ~~testb dh,dh high-byte aliasing~~ → fixed (read shift + write RMW)
- ~~\r character survival~~ → CR-stripped wad still fails
- ~~strlen haszero false positive~~ → differential test passes on all qwords
- ~~char-class table corruption~~ → chain pointers intact vs exe image
- ~~compare-mode global wrong~~ → mode=0 (case-fold loop active)

## Root cause hypothesis (highest confidence)

**Guest heap allocator returns overlapping blocks during rapid sequential
string allocation** (`M_StringDuplicate` calls `M_StringDuplicate` →
`I_Malloc` → guest malloc). When hundreds of strings are allocated in quick
succession during DEHACKED parsing, some allocations overlap, causing writes
to one string to corrupt others. `s_VERSION`'s heap block gets overwritten
by a neighboring allocation's data, resetting it to empty.

This is likely a WIE heap-allocation primitive bug (VirtualAlloc sizing,
page-granular rounding, or committed-vs-reserved tracking), not a JIT
codegen issue.

## Continuation plan

1. Instrument guest heap allocations during DEHACKED parse:
   - Log all `VirtualAlloc` calls with sizes/addresses during startup
   - Dump allocation map to identify overlaps
   - Compare against native Windows allocation layout
2. Alternatively: patch `M_StringDuplicate` in the guest binary to add
     sentinels around each allocation, then check sentinel integrity at exit
3. Or: run Doom Retro under WIE's iced interpreter (no JIT) with a very long
     timeout (>60 min) — if corruption persists, the bug is NOT JIT-specific
