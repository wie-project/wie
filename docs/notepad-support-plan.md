# Notepad Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** Draft (2026-08-03). Target locked: ReactOS notepad via `katahiromz/RNotepad` (LGPL-2.1+, standalone mingw build).

**Goal:** Make WIE run a classic Win32 notepad end-to-end — window, menu bar, multiline EDIT control with typing/selection/undo/clipboard/scrolling, status bar, Find/Replace, interactive file open/save, and registry-persisted settings.

**Architecture:** All gaps are in the existing host-side Win32 layer (`wie-winapi`, `wie-pe` resources, `wie-cli` GUI). The guest is a normal PE; notepad's menus mirror into the macOS top bar via the existing `MacMenuBar` (muda) and its EDIT control is host-side like every other control. No new crates; the only new tooling is a fetch/build script for the test binary. NOT-a-dialog-not-a-PE: notepad's Edit menu is a classic Win32 EDIT, so this is a depth-of-coverage milestone, not a new subsystem.

**Tech Stack:** Rust workspace (wie-pe → wie-cpu → wie-winapi → wie-runtime → wie-cli), winit/wgpu/muda GUI layer, mingw-w64 (`x86_64-w64-mingw32-gcc`) to build the guest, cmake (present; ninja absent → use "Unix Makefiles" generator).

### Known deviations (accepted)
- **Subclassed WndProcs**: RNotepad subclasses the EDIT (GWLP_WNDPROC) to update the status bar on navigation keys. Our host-side EDIT dispatch won't call the guest subclass; we instead deliver EN_HSCROLL/EN_VSCROLL/EN_CHANGE to the parent, which is what the subclass is for. The subclass becomes a pass-through no-op. Acceptable; verify nothing else in RNotepad depends on the subclass.
- **Alt-key mnemonics**: menus live in the macOS top bar, so `WM_SYSKEYDOWN` mnemonic activation is not needed for the milestone (synthesis exists if wanted later).
- **Print**: stubbed as cancel (PrintDlg returns FALSE) — real printing is out of scope.
- **Save-As hook**: RNotepad passes a custom-template hook (`DIALOG_ENCODING`); our policy/host dialog ignores hooks — encoding choices default to ANSI/UTF-8.

- [ ] **Step 1: Write the fetch script**

```bash
#!/usr/bin/env bash
# One-time setup: clone katahiromz/RNotepad and cross-build notepad.exe.
# Requires: git, cmake, x86_64-w64-mingw32-gcc (Homebrew mingw-w64).
set -euo pipefail
ROOT="$(cd "$(dirname "$0")/.." && pwd)"
SRC="$ROOT/.rnotepad-src"
DEST="$ROOT/real_exes"

if [[ -f "$DEST/notepad.exe" ]]; then
  echo "notepad.exe already present at $DEST/notepad.exe"
  file "$DEST/notepad.exe"
  exit 0
fi
mkdir -p "$DEST"
if [[ ! -d "$SRC" ]]; then
  git clone --depth 1 https://github.com/katahiromz/RNotepad "$SRC"
fi
cmake -S "$SRC" -B "$SRC/build" -G "Unix Makefiles" \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER=x86_64-w64-mingw32-gcc \
  -DCMAKE_RC_COMPILER=x86_64-w64-mingw32-windres
cmake --build "$SRC/build" --parallel
cp "$SRC/build/notepad.exe" "$DEST/notepad.exe"
file "$DEST/notepad.exe"
```

## Black background on resize (user report, 2026-08-03 — H1 confirmed by user)

**Symptom:** gui_edit (and notepad.exe, user suspects same cause) renders white at startup but the background turns BLACK after a host-window resize. EDIT text area stays white.

**User refinement (2026-08-03):** the white region is exactly the strip at the same HEIGHT as the multiline EDIT; the small strips ABOVE and BELOW the EDIT (the main window's client area not covered by the child) stay black. This pins the mechanism: the EDIT repaints itself (paint_edit fills its rect white), but the MAIN window's class-brush erase never runs after resize — `resize_window` sets `invalidated` without `ERASE_BACKGROUND`, so the DefWindowProc WM_PAINT fills nothing and the reallocated zeroed DIB strips upload black. The fix (lane active) sets `ERASE_BACKGROUND` on the resized window, which fills the class brush (gui_edit: COLOR_WINDOW+1 = white) over exactly those strips.

**Diagnosis (H1, confirmed):** the host render pass clears the surface white every frame, so the black is guest-frame content — the guest DIB is reallocated ZEROED on resize (present.rs:250 "fresh zeroed buffer", app.rs:621 "reallocates zero-padded"), and publishes are full-frame uploads (present_wgpu.rs:313-328), so any unpainted DIB area uploads as black. `resize_window` (session/window.rs:297-330) sets `invalidated = true` on the whole subtree but NEVER sets `ERASE_BACKGROUND`, so the DefWindowProc WM_PAINT after resize never fills the class brush (gui_edit: COLOR_WINDOW+1 = white). The startup path is white only because SetWindowPlacement (cb38299) sets both flags — resize never got the same treatment. Same root cause explains notepad's background black (startup case fixed by cb38299; resize case still broken).

**Fix (LANDED `69f214d` 2026-08-03):** `resize_window` now sets `invalidated + WindowFlags::ERASE_BACKGROUND` on the resized window (mirroring cb38299's SetWindowPlacement idiom); descendants keep `invalidated` only (EDIT paints its own white background — locked in by test). wie-winapi lib.rs exports `WindowFlags`. Failing-test-first at the real seam: session/window.rs unit test drives real `resize_window` on a real WinApiState (top-level + child) and asserts the record flags the erase pipeline reads (failed before: "must enter the repaint cycle"; passed after). Verification: wie-runtime all green (lib 14, micro_gui_window 10/10), wie-winapi 484, fmt clean, clippy clean on changed files (31 pre-existing wie-cpu), release rebuild + gui_edit selftest exit 0.

**⚠ Ordering residual risk (fix-29's own finding — next seam if the visual check still shows black):** app.rs `about_to_wait` posts WM_PAINT immediately after `resize_window`; GetMessage prefers queued messages over idle synthesis, and the DefWindowProc WM_PAINT case (message/mod.rs:722) clears `invalidated` + `ERASE_BACKGROUND` WITHOUT erasing — so the posted WM_PAINT may consume the flag before the erase fires. Startup is white only because the guest's empty-queue synthesis runs before any host post. If the user's interactive check shows persistent black strips: fix = DefWindowProc WM_PAINT should erase when the flag is set (erase-before-clear), or app.rs should not post WM_PAINT on resize. AWAITING user visual verification.

## Cross-cutting design note (2026-08-03, user directive)

**Immutable process-global handler config does NOT live in the global `WinApiState`.** Use `OnceLock<T>` (lazily initialized on first access), optionally shared between all handlers of a family: the UI language (Task 2.9), the host locale, and the wide env block (`__p__wenviron`, Task 2.12) are the current examples. Mutable per-session state (window records, control states, handle caches) stays in WinApiState. Precedent: the established OnceLock config accessors. New handler lanes must follow this unless the value is genuinely per-session mutable.

## Fidelity determination (ora-1, 2026-08-04 — user: "elements too small", "black background", "multiline doesn't mimic Windows"; mandate: pixel-perfect parity)

### Root causes (evidence)
1. **Size — guest 96-DPI logical pixels presented 1:1 physical, no device-scale factor anywhere.** Window created `with_inner_size(PhysicalSize::new(w,h))` (app.rs:717); grep: zero scale_factor reads in wie-cli. On 2× Retina the 640×480 guest window is 320×240 points = half the real app. Present is 1:1 (present_wgpu.rs:170-171, :284-288); the nearest sampler (:218-220) only scales when frame≠dst — equal at creation, so no upscale ever. Resize compounds it: WM_SIZE posts the PHYSICAL inner size as guest logical (app.rs:682-684), so after any resize the DIB is physical-px and stays proportionally small. Input is 1:1 too (app.rs:443-497; input.rs:76-78) — internally consistent, wrong at the window boundary.
2. **Black — host clear is already white (present_wgpu.rs:387-392); black comes from INSIDE the guest DIB: buffers are zero-initialized on every (re)alloc (present.rs:268 `vec![0u32; needed]`, :283) and notepad never erases its own background (WM_ERASEBKGND returns 1, main.c:408 — the class-brush/ERASE_BACKGROUND machinery is dead for notepad).** Any client pixel not covered by a child repaint between DIB realloc and the end of the paint cycle publishes as black (resize/settle races; the fix-29 erase-skip for erasing windows; DefWindowProc WM_PAINT consumes invalidated+ERASE_BACKGROUND without erasing — message/mod.rs:722). Menu bar is native (muda) — not a source.
3. **Multiline EDIT gaps (priority order):** #1 Lucida Console (STRING_DEFAULTFONT) → Named → fontdb miss → **sans-serif** (font_system.rs:84-97; notepad sets FIXED_PITCH|FF_MODERN, settings.c:120) — dominant: proportional text in the editor; #2 line height excludes external leading (font_system.rs:341-343 — line_gap parsed, never added); #3 no caret blink (zero timer hits in edit.rs/controls); #4 typing at the bottom doesn't auto-scroll (only programmatic EM_SCROLLCARET minimal-scroll); #5 EN_HSCROLL/EN_VSCROLL gaps (fix-42 landed PgUp/PgDn; arrow/click status-bar refresh via the subclass bridge still to verify); #6 scrollbar chrome absent (wrap-off shows no V-scrollbar; gutter painted white — not black, missing chrome); #7 disabled-state rendering unverified (low).

### Decisive approach (ora-1)
**Logical-96-DPI guest space × device scale factor at the window boundary; nearest upscale in the existing blit; all input ÷ scale factor.**
- Window creation: `with_inner_size(LogicalSize::new(w,h))` (app.rs:717) — winit multiplies by the scale factor itself.
- Surface/staging: NO restructuring — the fullscreen triangle + sampler already implement frame≠dst upscale; the surface already tracks inner_size (physical) via :284-288.
- Input: ÷sf before mouse_target/post_message (app.rs:443-497; CursorMoved/MouseInput/MouseWheel/Moved/DroppedFile point; double-click slop ×sf, input.rs:67); MSG.pt in logical px.
- Resize settle: WM_SIZE = physical ÷ sf (app.rs:682-684); apply_host_geometry ×sf (app.rs:125-134).
- Black: erase-before-clear in DefWindowProc WM_PAINT (message/mod.rs:722) + full-surface host fill with the window's class-brush color (COLOR_WINDOW for notepad, COLOR_BTNFACE for dialogs) before the blit; test invariant: the idle published frame (headless `record` slot, present.rs:145) contains zero 0x000000 pixels outside legitimately black content.
- Judgment calls (flagged, not hidden): (1) nearest vs linear at fractional factors — nearest wins (integer factors dominate on macOS; linear blurs everything); (2) **at 2×, nearest-upscaled 96-DPI raster text is blockier than Windows' 2× vector re-render — accepted unless the user demands crisp 2× text (then: paint the DIB at device resolution, rasterize glyphs at sf×, present 1:1 — a paint-layer-wide change with higher repaint cost; the ~55 ms repaint at 886×776 scales superlinearly with resolution)** — **USER DECISION 2026-08-04: fast path confirmed ("Fast: upscale at present (Recommended)")**; (3) fixed 640×480 CW_USEDEFAULT cascade deviation — accepted.

## Paint/rendering system design (ora-1, 2026-08-04 — user: "modular, efficient, simple to manipulate")

### Map (5 layers)

Modularity: 4 homes for "how do I paint X" (controls/{button,edit,listbox,static}.rs + paint.rs + gdi32 blit.rs + text.rs); manual offset threading (info.offset_x.saturating_add everywhere; fill_rect_clipped exists because primitives don't clip); the font take/put borrow dance repeated at every paint entry; duplicate color tables (controls/mod.rs:107-121 hardcodes COLOR_* while geom.rs sys_color holds the same — drift risk); the bundle refactor half-landed (PaintCtx/PaintFont/Rect/TextGeom/HitTestLayout defined but only listbox consumes them). Simplicity: 9-13-arg signatures + borrow dance + manual offset math.

### Target architecture (decisive)
**Axis 1 — modularity: finish the bundle direction as PRIMITIVE METHODS on PaintCtx (the single canvas object), not more threaded bundles.** PaintCtx gains `info: ResolvedWindow` + `font: Option<PaintFont>`; methods `fill_clipped(rect, color)`, `fill_surface(rect, color)`, `text(x, y, text, color)`, `text_advance(text)`, `rect(x,y,cx,cy)`; the take/put happens ONCE in paint_control; signatures collapse to ≤3 args (paint_edit(ctx, text, TextGeom) etc.); HitTestLayout stays for the hit-test path. **Axis 3 — simplicity: subsumed by Axis 1** (one object, one module, no offset math, no take/put, ≤3-arg signatures, one color table).

### Refined determination (ora-2, read the actual mid-edit tree)
- **Decision (a): direct writes stay, behind a `SurfaceTarget<'a>{pixels, width, height, clip}` handle threaded from paint_control — NOT a command list.** Three grounds: (1) the B1 surface hand-back (publish moves the buffer into the published Arc; the next paint hands it back) FORBIDS deferred execution — a command list executed after publish would write into a possibly-published buffer, needing a second compositing buffer (2× memory + copy) for one consumer; (2) YAGNI — the only consumer is the full-frame upload; the pixel-assert tests + zero-0x000000 invariant need a byte-identical executor that doesn't exist; (3) the 2×-text future is a `scale`/`height_px` parameter change (the FontEngine already caches glyphs per (font, height, codepoint) — font_system.rs:402), not an architecture change. Flagged judgment call.
- **Decision (b): per-window dirty-rect UNION at the surface + sub-rect GPU upload + full-frame fallback on skipped present.** The ~55 ms is guest-driven repaint (dirty rects don't cut it — the invalidated flag + WM_PAINT clip already give window-level invalidation); what dirty rects cut is the per-publish 4 MB upload for small-delta frames (caret blink 530 ms). Mechanics: every write primitive unions its bounds into `WindowSurface.dirty: IRect`; `SurfaceFrame.region: Option<IRect>` (None = full); wgpu uploads via write_texture origin/extent. The B2 objection (region-delta can't survive present skipping) is solved by carrying the region on the SURFACE (survives the coalesced drain) + a generation-gap rule (host uploads full when it skipped/dropped a present; Arc::ptr_eq skip stays — orthogonal). NOT a per-primitive region system (subtract_rect exists but violates YAGNI until a second consumer).
- **Decision (c): keep the winapi-paint vs wgpu-present split (the SurfaceFrame seam is the tested interface — headless record, ptr_eq skip, background clear, per-window registry, pixel tests all hang off it); restructure only the winapi side:** (1) `paint_control` + the status-bar painters move from button.rs to paint.rs (SRP — button.rs owns button state, paint.rs owns paint dispatch); (2) UNIFY RECTS — delete `controls::Rect`, use `IRect` everywhere (it already has from_xywh); (3) extend the bundle: PaintCtx gains the resolved destination + clip + scale; `render_text_into_surface` is already a target signature (text.rs:866) — make `fill_rect_surface` match it, which hoists ensure_surface from per-fill to once per paint_control (kills the per-fill hash churn).
- **Untraced/flagged:** the 55 ms attribution (guest-driven repaint) is inference from comments, not a profile — lane 3's acceptance includes a WIE_RUNTIME_PROFILE check that present_ns drops on caret blink.

## Effort shape

Phases 1 (menus/accel) and 3 (status bar) are small and unblock the demo fast. Phase 2 (multiline EDIT) is ~60% of the work. Phase 4 (dialogs) is the second-biggest chunk. Phases 0/5/6 are thin. Recommended order: 0 → 1 → 2 → 3 → 4 → 5 → 6.
